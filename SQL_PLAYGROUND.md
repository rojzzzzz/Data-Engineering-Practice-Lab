# SQL playground

Open **Practice → Open SQL practice**, select an exercise, inspect its schema and samples, then start it. Run executes the selected text, or the entire active tab when nothing is selected. Ctrl/Cmd+Enter is the keyboard equivalent. Check answer evaluates every named answer tab; Scratch is never graded. Explain shows DuckDB's physical plan. Drafts autosave after 750 ms or on blur and travel with progress backups. Results stay in the browser session, not the backup.

The bundled nine exercises use DuckDB 1.5.5, including recursive CTEs and window functions. SQL-008, SQL-010 and SQL-011 retain their written workflow. PostgreSQL-specific functions are not automatically translated. Small fixture timings do not establish production-scale performance.

Checks return only pass/fail and broad failure categories. Equivalent queries are accepted; duplicates, NULLs, ordering where requested, and numeric precision count. Money must use exact decimal arithmetic. Private fixtures, expected results and reference SQL are never rendered in the student workspace. This is a local practice tool: someone with access to its source files can read the bundled assessment metadata.

## Run and build

Install `requirements.txt` into your environment and run `streamlit run app.py`. No Node.js or separate database server is needed at runtime. For frontend changes, run `npm ci`, `npm run format`, `npm test`, `npm run format:check`, and `npm run build` inside `erd_frontend`. Both editor bundles are generated. Docker builds these bundles from the lockfile.

`PRACTICE_DB_PATH` optionally points to a separate SQLite database for testing. It defaults to `database/practice.db`. Existing attempts migrate automatically; old backups remain importable. Prose, diagram and SQL workspace writes are independent.

## Author executable questions

Add optional `sql_playground` metadata to a normal challenge. The complete examples in `data/challenges.json` are generated by `scripts/build_sql_exercises.py`; that script updates only the nine bundled SQL exercises. New questions require metadata, not Python application changes.

```json
{
  "version": 1,
  "dialect": "duckdb",
  "tables": [{
    "name": "orders", "description": "One row per order",
    "columns": [
      {"name": "id", "type": "BIGINT", "nullable": false, "key": "Primary key"},
      {"name": "amount", "type": "DECIMAL(12,2)", "nullable": true, "key": ""}
    ]
  }],
  "visible_fixture": {"orders": [[1, "10.50"], [2, null]]},
  "tasks": [{
    "id": "total", "title": "Total revenue",
    "description": "Return one decimal total, ignoring NULL amounts; zero when no amount exists.",
    "ordered": false,
    "columns": [{"name": "total", "type": "decimal", "scale": 2}]
  }],
  "assessment": {
    "fixtures": [{"orders": []}, {"orders": [[3, "-2.50"], [4, "2.50"]]}],
    "reference_queries": {"total": "SELECT CAST(COALESCE(SUM(amount),0) AS DECIMAL(18,2)) AS total FROM orders"}
  }
}
```

Use valid SQL identifiers for tables, columns, and task IDs; `scratch` is reserved. Supported source types are INTEGER, BIGINT, DOUBLE, BOOLEAN, VARCHAR, DATE, TIMESTAMP, and DECIMAL(precision,scale). Keys are documentation, not enforced constraints. Represent decimal money as JSON strings, dates as ISO strings, and NULL as JSON null. Every fixture must contain every declared table. Include a visible fixture and two to five different private fixtures; use ties, boundary dates, duplicate facts, missing matches, and empty inputs deliberately.

Output types are integer, decimal, number, string, date, timestamp, and boolean. Decimal/number columns require scale 0–8; comparison rounds half away from zero. Output column names and order must match the task. `ordered` controls row ordering, not duplicate preservation. Define business decisions in the description rather than assuming the reference solution's choices are universal.

Use an `exercise_context` table for fixed reporting dates. Do not depend on CURRENT_DATE, randomness, external files, or network services. References must be single SELECT queries and satisfy the output contract on every fixture. Import preview executes bounded reference checks before allowing the bank to be applied. Reference validation proves executability and output shape, not the business correctness of an AI-generated solution; review the business rules and add known-wrong-answer tests.

## Limits and checks

Each job uses a fresh process and in-memory database. External access, extension installation/loading, Python replacement scans, configuration changes, writes and multiple statements are disabled. Queries have a ten-second worker watchdog; assessments have a thirty-second overall deadline. DuckDB uses two threads, a 256 MB engine memory setting and no disk spill. The memory setting is not a hard process-memory sandbox; this is intended for local personal use.

Run previews stop at 1,000 rows or 2 MB; downloads contain only displayed rows. Assessments compare full bounded outputs (10,000 rows / 2 MB), and report a resource failure rather than accepting truncated results. Each fixture allows up to 10,000 rows per table; the complete exercise is limited to 4 MB.

Run `python -m pytest -q` for engine, content, comparison, privacy, persistence, timeout/cancellation and Streamlit integration coverage. Run and Check submit the current editor draft, not a previous autosave. Editing answers or changing exercise metadata makes saved checks outdated.

## Verification measurements

The implementation passed 99 Python tests, frontend tests, TypeScript checking, formatting, and both production bundle builds. All nine reference assessments also passed inside the Docker image. A representative Windows Run took 2.40 seconds end to end and a SQL-001 assessment took 2.12 seconds. Docker Run took 1.11 seconds; all nine assessments together took 21.59 seconds. These are single local measurements, not guarantees. Query execution itself was under 1 ms for SELECT 42; disposable-process startup and fixture loading dominate. The under-one-second end-to-end Run target is not yet met on this machine.
